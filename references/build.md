# Build a direction into a working product

Use when making a new interface, taking a selected study into a usable product,
or integrating real content and behavior into an established direction. A clear
local repair stays direct. [Design direction](design-direction.md) owns choosing
the direction; this method owns carrying it through construction.

## Keep the chosen thing available

Read the actual reference or candidate, the feedback attached to it, and the
current product contract. Keep a retrievable version or authorized artifact
pointer in the existing project design record when the work spans sessions.
An adjective summary cannot substitute for seeing the chosen composition.

| Input | Carry into implementation | Do not infer |
| --- | --- | --- |
| Keywords or short descriptions | Product-specific attention, density, reading, material, and interaction choices | A universal palette or template; that missing taste history means missing task context |
| Reference image | Its requested relationships and scope: exact match, translated language, or one borrowed quality | Unrelated copy, branding, data, or workflow |
| “B works; remove the big heading; continue” | B as the selected direction with that explicit correction | That every incidental detail is approved, or why the person preferred B |
| “No” on a candidate | Reopen that candidate's premise at the scope of the rejection | A permanent dislike of every ingredient, or permission to reduce a whole-result rejection to one cosmetic tweak |

Translate the selected result into a few working commitments: what leads,
what stays subordinate, what the user can do nearby, and what should remain
recognizable after integration. Mark your explanation of *why* it works as a
design judgment, separate from the actual feedback. Incomplete feedback is
usable evidence; the user need not supply a design essay before work resumes.

Provisional taste judgments are not execution holds. Continue authorized,
reversible work using the best supported interpretation. Ask only when a new
tradeoff changes the intended product or crosses the caller's actual authority.

## Build through the decisive task

Choose the smallest complete path that exposes the difficult relationship,
then finish the full requested surface. For a record tool, that might mean
opening an existing entry, amending one value, saving, and reopening it while
retaining the other values. For a reader, it might be opening a long article,
following a reference, and returning to the reading position. A hero or happy
state alone cannot exercise these promises.

Inspect the real content and data path early. Use authorized representative
inputs where live data is unavailable, labeling them as fixtures. Include the
variation that challenges this design: uneven record lengths, missing values,
an active edit, or an actual supported failure. Do not invent every possible
edge case or postpone difficult content until the layout has hardened.

Implement structure and behavior together:

- Give the primary subject and action a deliberate spatial relationship using
  [visual construction](visual-construction.md). Component defaults are useful
  materials, not authority to replace the selected experience.
- Map objects and actions with [App interaction](app-interaction.md). A visible
  input already makes a promise about what deserves attention and action.
- Follow [state and contracts](state-contracts.md) when data ownership or update
  semantics determine whether that action can work. A convenient whole-record
  endpoint must not silently turn nearby editing back into a full questionnaire.
- Put each meaningful state into the same visual language. Empty content, long
  text, pending work, and recovery are parts of the design, not default library
  screens pasted on after the attractive state.

Keep engineering and method explanations in the usage note or handoff unless
they help a person make a real product decision. The screen needs useful units,
scope, and honest feedback; it does not need to announce the fixture, absence
of a CDN, or every design prohibition the implementer followed.

For example, preserving an airy record overview does not mean truncating real
notes or shrinking type to preserve its empty area. Regroup metadata, constrain
reading width, and let the appropriate region grow. Preserve the selected
relationship through changed content, rather than freezing sample geometry.

## Follow the cause across implementation layers

Current source explains how the product works; the accepted task determines
what must change. Preserve unaffected promises and adopted technology while
repairing the part the request actually changes. Internal component, state,
API, and storage-code boundaries do not by themselves require new permission.

Preparatory refactoring is justified by observed resistance in this change:
duplicated state that falls out of sync, a shared component whose switches
erase necessary differences, or a save path that cannot express the selected
operation. Name that resistance, correct the responsible scope, retire the
superseded path, and return to the original task. “Cleaner architecture” or
possible future reuse alone does not justify a new framework or theme engine.

Separate behavior-preserving restructuring from changing product meaning,
public contracts, or stored facts. Use the host/repository engineering method
for investigation, migration, tests, Git, and external actions. Existing task
authority continues to apply; this method adds no approval layer and grants
no new account, production, data-transfer, or destructive authority. FC remains
responsible for closing the experience even when the cause lives outside a
frontend directory. No particular engineering plugin is required.

## Compare while integrating

After a meaningful rendered slice, revisit the actual selected artifact and
the task it now serves. Check both what the controls do and whether the chosen
quality survived. When the result drifts, identify the integration decision
responsible: default component geometry, global tokens, content compression,
new interaction depth, or a change in state ownership. Fix that cause while it
is local instead of saving a visual rebuild for the end.

Use [interface scenarios](interface-scenarios.md) when the important state
should be reopened during subsequent work. Preserve useful prototype code when
it fits the product; replace temporary code when needed without discarding the
selected design. Browser-only experiments must return to the canonical source
before they count as implementation.

## Close the promised surface

An exploratory prototype may intentionally answer one question. Match its
fidelity to that question: representative content for layout, operable editing
for interaction, and a reopened state for return use. Give alternatives
comparable care so obvious defects do not determine the selection.

Once a usable first product is requested, complete its core paths, real state,
coherent visuals, and applicable [QA](qa-contract.md). An early version or
“demo” label does not excuse fake saving, unreadable content, or unresolved
composition. Report what is integrated and what the evidence actually shows;
owner aesthetic acceptance remains separate.
