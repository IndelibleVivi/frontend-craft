# Maintainer forward cases

Use for a substantial change to this method, not for every frontend task.
Select only cases that distinguish the changed behavior. Package validation
checks structure; these cases inspect actual choices and artifacts.

Use synthetic/public-safe material in an isolated workspace. Keep raw exports,
personal feedback, project secrets, and private instructions out of evaluation
handoffs. Permission to evaluate does not authorize external services,
installation, publication, or account operations. An independent evaluator is
useful when available and authorized; do not spawn one just to fill a ritual.

Give the executing agent the user request, candidate skill, and raw fixture
only. Withhold the observations below and any later feedback until that phase
occurs. For an old/new comparison use separate clean contexts and the same
initial inputs/model/tool conditions; never give the candidate the old run's
later corrections. A single candidate run is a smoke test, not an A/B result.

| Case / request seed | Discriminating observation for the maintainer |
| --- | --- |
| Clear repair: change one named label color, preserve the rest | No design interview, global redesign, new design record, or unnecessary framework method; focused rendered check |
| Open direction: build a usable comparison tool with long mixed-script records | Concrete content/attention/density decisions and working workflow, not a hero-only shell or flattering invented content |
| Explicit style: use cards and an expressive gradient for a playful visual editor | Implements the requested style without applying an aesthetic blacklist; controls still legible |
| Revision: owner accepts the work's typography and palette but calls its controls confusing | Repairs object/scope/action comprehension while preserving the accepted work; checks original complaint and nearby regression |
| Repeated complaint: “still wrong” with evidence of an old served build | Checks active runtime before repeating or amplifying the same style change |
| Review-only: inspect an existing interface and explain why it feels empty | Located observations and hypotheses; no unauthorized edits or fabricated browser evidence |
| A workbench and a share image with the same identity | Different composition for usage versus publication; verifies the actual export at intended reading size |
| Feedback scope: a user approves a multi-change version and says “keep this vivid style for this poster” | Records local acceptance without claiming which variable caused it or turning it into a universal workspace preference |
| Delivery compromise: “ship this for now; the navigation still bothers me” | Treats shipping and aesthetic acceptance separately; preserves unresolved status |
| Native UI with no device tools | Uses applicable source/available evidence and names the missing native layer without claiming browser QA proves native behavior |
| Procedural visual work: subject still lacks the desired depth | Works on the expressive subject before growing controls; observes temporal/interactive qualities where in scope |
| Visual goal: translate a supplied game's UI art direction into an editable photo composition, while keeping the editor's own identity | Extracts relationships from the real reference, checks a revealing render against that goal, and develops the missing mechanism without turning every photo into a menu or silently changing the product into a generic poster tool |
| Stateful editor: browse a candidate, drag an image within a fixed crop window, then cancel | Keeps preview separate from adoption, targets the right object, restores the draft, and checks meaningful history through actual controls |
| App-wide polish: Home is attractive, long conversations and search are still cumbersome | Covers the requested journeys and realistic content; does not declare the whole App finished from Home evidence |
| Creative-tool study: a hand-refined export looks strong, but users cannot reproduce or reopen it | Labels the manual result accurately and returns the claimed capability plus editable work to the supported product path |
| Whole direction rejected, with a dark focus ring named as one disliked detail | Records the full rejection, revisits the visual direction, and designs a perceivable focus state; does not collapse feedback into one CSS change or remove keyboard location |
| Growing records: query for an editor issue with an explicit current boundary, unrelated project cases, and an old superseded preference | Reads current context in full; filters case scope and lifecycle before ranking; preserves evidence basis/outcome and reports retrieval limits; a lexical miss does not erase the boundary |
| Feedback changes within one scope while a different project's choice remains accepted | Revises the proper current entry, links a replacement case when needed, retires the old active conclusion, preserves the other scope, and reads back the result |
| Conversational brief: “I want to make something worth sending; the tool should get out of my way” with an existing two-format editor | Reconstructs author versus reader needs, preserves both real formats and editable content, separates inference from explicit requirements, and judges the actual work at sharing scale |
| Reference adjectives conflict with the product's real use: an expressive work inside a long-use workspace | Locates which surface owns expression; does not copy reference labels, fictional facts, or every animation into the editor |
| Installed semantic retrieval: ask in Chinese for an English case with no literal overlap, alongside an opposite recommendation and retired case | Uses the configured backend, resolves current local revisions, returns relevant bounded candidates with scope/status, and does not interpret semantic similarity as preference authority |
| Record a rejected design mechanism, revise the record, then use it on a later related task | The stored case can be found and changes an identifiable choice; changed, retired, or deleted vectors cannot return old evidence; the new render is inspected without inventing owner approval |
| Borrow a useful mechanism from a different project | Explicit transfer returns its origin as an analogy; default scope stays isolated and colors, branding, or local acceptance do not travel with the mechanism |
| Playful request for editable share-card copy, attribution, numeral styling, and ornament, alongside two local layout complaints | Treats the request seriously, reconstructs the positive sharing/authorship goal, implements real editable ownership, and stores the wish as requested rather than falsely accepted; does not reduce it to a negative checklist or global ornament preference |
| A functioning poster editor passes interaction checks, but its poster is rejected for both weak composition and personal mismatch | Inspects the work independently at publication scale, distinguishes task fit/craft/personal fit, and corrects a named visual relationship; records the rejection without turning a causal hypothesis or an entire visual ingredient into a personal prohibition |

Use actual execution for at least one consequential changed path when feasible;
a written explanation of what the agent would do proves only method selection.
For a revision case, preserve the first artifact before delivering feedback.
Inspect generated source, rendered result, interaction evidence, and any record
updates. Don't score self-reported compliance or merely count keywords.

Keep a short private result: initial input, candidate revision, environment,
artifact/evidence pointers, observed decisions, failure or limit, and any
resulting method change. Do not commit raw evaluation traces by default.

Track everyday outcomes only when there is evidence: whether the first
direction survived, whether the same correction had to be repeated, and whether
accepted qualities regressed. New ideas are not failures. Silence is unknown.
Do not manufacture a hit-rate percentage from this scenario menu, agent effort,
or unobserved user satisfaction.
